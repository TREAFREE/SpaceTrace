# SQLite 恢复生命周期

SpaceTrace 把数据库启动失败视为“需要恢复的事故”，绝不会把它当成静默新建数据库、覆盖用户历史的许可。

1. 从已发布 schema 开始迁移前，使用 SQLite Online Backup 在数据库同目录生成完整临时副本，再通过同一文件系统内的 `rename(2)` 原子发布为 `SpaceTrace.sqlite.pre-migration-vN.sqlite`。
2. 迁移及仓储启动成功后删除该备份；迁移失败则保留。
3. SQLite 有机会修改文件之前，先校验主库文件头和 WAL 的基本帧结构。
4. 遇到迁移失败、数据库损坏、磁盘写满、不支持的 schema 或未知启动错误时，把主库、WAL、SHM 和迁移备份复制到权限受限的 `Recovery/<事故编号>`。原始文件不会被删除或重置。
5. 只读恢复优先打开迁移前备份，其次打开隔离的主库快照。连接使用 immutable URI、只读模式和 `query_only`；此时 App 不会启动扫描和磁盘监听。

恢复清单只包含失败原因、时间与文件名，不保存用户目录的绝对路径。当前 WAL 校验可以发现截断和明显错误的帧结构；更深的页级诊断应由未来的显式离线修复工具承担。

对应验证位于 `SQLiteDatabaseRecoveryTests`，覆盖原子备份保留/清理、主库与 WAL 的逐字节隔离、只读来源选择以及写入拒绝。
